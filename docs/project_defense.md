## 1. Постановка задачи

Банк хранит данные о покупках и переводах своих клиентов. Задача — на основе поведения клиента за последние 3 месяца:

1. **Понять клиента**: куда он тратит деньги, сколько получает, какими операциями пользуется.
2. **Выбрать один продукт** из линейки банка, который принесёт клиенту наибольшую выгоду.
3. **Сформулировать push-уведомление**: короткое, персональное, по правилам редполитики банка.

**Результат работы** — CSV-файл `data_output/personalized_recommendations.csv`:

| client_code | product | push_notification |
|---|---|---|
| 1 | Кредитная карта | текст уведомления |
| … | … | … |

**Почему это полезно банку:** вместо массовой рассылки «всем одно и то же» клиент получает предложение, которое соответствует его реальным тратам. Это повышает конверсию и снижает раздражение от нерелевантной рекламы.

## 2. Входные данные

Папка `data_intput/` (название с опечаткой, но код использует именно его). На каждого клиента по два файла:

### 2.1 `client_N_transactions_3m.csv` — покупки по карте

| Колонка | Пример | Смысл |
|---|---|---|
| client_code | 1 | ID клиента |
| name | Айгерим | имя |
| product | Карта для путешествий | эталонный продукт (см. ниже) |
| status | зп | статус клиента (зарплатный, студент, премиальный, стандартный) |
| city | Алматы | город |
| date | 2025-06-01 09:10:36 | дата и время |
| category | Такси | категория покупки |
| amount | 6424.48 | сумма |
| currency | KZT | валюта |

Объём: ~17 400 строк у 58 клиентов. Почти всё в KZT, 35 операций в EUR. У клиентов **34 и 45 этого файла нет**.

### 2.2 `client_N_transfers_3m.csv` — переводы и движения денег

Те же колонки, плюс:

| Колонка | Пример | Смысл |
|---|---|---|
| type | salary_in, p2p_out, fx_buy… | тип операции |
| direction | in / out | входящая или исходящая |

Объём: ~18 000 строк у всех 60 клиентов. Самые частые типы: `card_out` (8 829), `p2p_out` (3 600), `atm_withdrawal` (1 152), `card_in`, `utilities_out`, `loan_payment_out`, `cashback_in`. Есть и «продуктовые» сигналы: `fx_buy`/`fx_sell` (обмен валют), `gold_buy_out`/`gold_sell_in` (золото), `invest_out`/`invest_in`, `deposit_topup_out`, `cc_repayment_out`, `installment_payment_out`.

### 2.3 Колонка `product`

Распределена ровно по 6 клиентов на каждый из 10 продуктов. Это **эталонная разметка** — правильный ответ, с которым можно сравнивать рекомендации. Как признак её использовать нельзя: это была бы утечка ответа (data leakage).

## 3. Архитектура и поток данных

```
                    ┌──────────────┐
                    │   main.py    │  запуск, итоговая статистика
                    └──────┬───────┘
                           │
                ┌──────────▼───────────┐
                │ back/csvgenerator.py │  цикл по клиентам 1..60
                └──┬────────┬────────┬─┘
                   │        │        │
     ┌─────────────▼──┐ ┌───▼────────────────┐ ┌▼──────────────────────┐
     │ ai/analytics.py│ │ai/product_analyzer │ │ ai/recommendations.py │
     │ CSV → профиль  │ │профиль → продукт   │ │ продукт → текст пуша  │
     └────────────────┘ └────────────────────┘ └───────────────────────┘
                           │
                ┌──────────▼──────────────────────────────┐
                │ data_output/personalized_recommendations│
                └─────────────────────────────────────────┘
```

Путь одного клиента через систему:

```
client_7_transfers_3m.csv  ─┐
client_7_transactions_3m.csv┴─► Analytics.analyze_client(7)
                                  → {name, city, status, total_transfer_in, ..., top_categories}
                             ─► ProductAnalyzer.analyze_products(profile)
                                  → {name: "Премиальная карта", score: 531.4, all_scores: {...}}
                             ─► llm_generate_push(name, product, top3, benefit)
                                  → "текст пуша"
                             ─► строка в итоговом CSV
```

### Почему архитектура именно такая

- **Разделение ответственности.** Каждый модуль решает одну задачу: данные, бизнес-логика, текст, вывод. Их можно разрабатывать и тестировать по отдельности.
- **Заменяемость.** Правила скоринга можно заменить ML-моделью, а LLM — шаблонами, не трогая остальные модули. Интерфейс между ними — обычный словарь Python.
- **Папка `ai/`** содержит всю «интеллектуальную» часть, **`back/`** — серверную обвязку, **`myapp/`** — задел под Django-приложение.

## 4. Модуль `main.py` — точка входа

Файл: [main.py](../main.py)

### Что делает

1. Добавляет корень проекта в `sys.path`, чтобы работали импорты вида `from back.csvgenerator import ...` независимо от того, из какой папки запущен скрипт.
2. Создаёт `CSVGenerator`.
3. Вызывает `process_all_clients()` — основной расчёт.
4. Сохраняет результат через `save_results(results, "personalized_recommendations.csv")`.
5. Считает статистику: сколько клиентов получили каждый продукт.
   ```python
   products = {}
   for result in results:
       products[product] = products.get(product, 0) + 1
   ```
6. Печатает первые 3 уведомления как пример.
7. Возвращает код выхода: `0` — успех, `1` — ошибка.

### Почему так

- **Один вход в систему.** Пользователю не нужно знать внутреннюю структуру: достаточно `python main.py`.
- **`try/except` с `traceback.print_exc()`** — при падении видно и короткое сообщение, и полный стек вызовов для отладки.
- **Код выхода через `sys.exit(exit_code)`** — стандарт для консольных утилит: скрипт можно встроить в планировщик (cron, CI), который по коду поймёт, успешно ли прошёл запуск.
- **Статистика по продуктам** — быстрая проверка адекватности: если всем выпал один продукт, это видно сразу.

## 5. Модуль `back/csvgenerator.py` — оркестратор

Файл: [back/csvgenerator.py](../back/csvgenerator.py)

### Класс `CSVGenerator`

#### `__init__(data_input_path="data_intput", data_output_path="data_output")`

Создаёт два рабочих объекта:
- `self.analytics = Analytics(...)` — с путями к данным;
- `self.product_analyzer = ProductAnalyzer()` — с каталогом продуктов.

**Почему:** объекты создаются один раз, а не на каждого клиента. Пути передаются параметрами, поэтому их можно поменять без правки кода (например, для тестовых данных).

#### `process_all_clients()`

Для каждого `client_code` от 1 до 60:

1. `client_data = self.analytics.analyze_client(client_code)` — профиль клиента.
2. `best_product = self.product_analyzer.analyze_products(client_data)` — лучший продукт.
3. Подготовка данных для текста:
   - `top_categories = list(client_data['top_categories'].keys())[:3]` — три главные категории трат;
   - `benefit_sum = best_product['score'] * 1000` — «ожидаемая выгода» (оценка, умноженная на 1000, чтобы вернуть масштаб в тенге — см. ограничения).
4. `llm_generate_push(...)` — текст уведомления.
5. Добавление строки `{client_code, product, push_notification}` в результат.

**Обработка ошибок:** каждый клиент обёрнут в собственный `try/except`. Если у клиента нет файла или данные битые, в результат попадает строка «Ошибка обработки», а цикл продолжается.

**Почему так:** в пакетной обработке одна плохая запись не должна ронять весь запуск. На выходе всегда 60 строк — по одной на клиента, и сразу видно, у кого проблема.

#### `save_results(results, filename="recommendations.csv")`

- Превращает список словарей в `pandas.DataFrame`.
- Создаёт папку `data_output`, если её нет (`mkdir(exist_ok=True)` — не падает, если папка уже есть).
- Пишет CSV в UTF-8 без индекса (`index=False`) — чтобы в файле не было лишней колонки с номерами строк.
- Возвращает путь к файлу.

#### `main()` внутри модуля

Позволяет запустить генератор напрямую: `python back/csvgenerator.py`. Для этого в начале файла корень проекта добавляется в `sys.path`.

### Особенности

- `import django` в начале файла сейчас не используется — это остаток задела под веб-часть. Django при этом нет в `requirements.txt`, так что импорт упадёт на «чистом» окружении.
- Список клиентов задан жёстко (`range(1, 61)`), а папка вывода в `save_results` захардкожена как `"data_output"` и не берёт значение из конструктора.

## 6. Модуль `ai/analytics.py` — аналитика клиента

Файл: [ai/analytics.py](../ai/analytics.py)

Задача модуля — превратить «сырые» строки операций в компактный **профиль клиента** (набор признаков), с которым дальше работает скоринг.

### `__init__(data_input_path, data_output_path)`

Сохраняет пути как объекты `pathlib.Path`.
**Почему `Path`:** одинаково работает на Windows и Linux, пути склеиваются оператором `/` без возни со слешами.

### `load_csv(filename)`

Читает CSV через `pd.read_csv`. Если файла нет — выбрасывается `FileNotFoundError`, который перехватывается выше.

### `clean_data(df, date_col="date", amount_col="amount")`

| Шаг | Код | Зачем |
|---|---|---|
| 1 | `df.dropna()` | убрать строки с пропусками — по ним нельзя посчитать признаки |
| 2 | `df.drop_duplicates()` | убрать задвоенные операции, иначе суммы завышаются |
| 3 | `pd.to_datetime(..., errors="coerce")` | привести дату к типу datetime; некорректная дата станет `NaT`, а не уронит программу |
| 4 | `pd.to_numeric(..., errors="coerce")` | гарантировать, что сумма — число |
| 5 | `df[df[amount_col] > 0]` | убрать нулевые и отрицательные суммы; направление денег задаётся колонкой `direction`, а не знаком |

**Почему так:** реальные банковские выгрузки бывают «грязными». Очистка в одном месте гарантирует, что все дальнейшие расчёты работают с корректными данными.

### `analyze_client(client_code)` — главный метод

1. Загружает и очищает оба файла клиента.
2. Берёт **имя, город, статус** из первой строки переводов (или покупок, если переводов нет).
3. Считает признаки:

| Признак | Как считается | Что означает |
|---|---|---|
| `total_transfer_in` | сумма `amount`, где `direction == "in"` | сколько денег пришло за 3 месяца |
| `total_transfer_out` | сумма `amount`, где `direction == "out"` | сколько ушло |
| `avg_monthly_balance_KZT` | `total_transfer_in / 3` | средний месячный приход (используется как оценка «баланса») |
| `transaction_sum` | сумма всех покупок | общий объём трат по карте |
| `transaction_avg` | средний чек | сейчас дальше не используется |
| `top_categories` | `groupby("category").sum()` → сортировка → `head(5)` → `dict` | 5 категорий с наибольшими тратами: `{"Такси": 210000, ...}` |
| `age` | константа 30 | возраста в данных нет |

**Почему такие признаки:**
- Продукты банка завязаны именно на них: кешбэк — на категории трат, депозиты и премиальная карта — на остаток денег, кредит — на соотношение доходов и расходов.
- **Топ-5 категорий** — компромисс: достаточно, чтобы увидеть основные привычки, и не перегружает расчёт мелкими тратами.
- **Деление на 3** переводит сумму за период в месячное значение, потому что пороги продуктов (например, 1 млн ₸ для премиальной карты) заданы помесячно.

### `analyze_all(clients)` и `save_report(df, filename)`

Вспомогательные методы: собирают профили всех клиентов в одну таблицу и сохраняют её как аналитический отчёт. В основном конвейере не используются, но полезны для исследования данных (посмотреть распределения доходов, трат и т.п.).

### Особенности

- Пути по умолчанию в конструкторе — `"data-input"`, `"data-output"` — не совпадают с реальными папками; работает только потому, что `CSVGenerator` передаёт правильные пути.
- Валюты не конвертируются: суммы в EUR складываются с KZT как есть.
- Статус клиента извлекается, но в скоринге не участвует.

## 7. Модуль `ai/product_analyzer.py` — выбор продукта

Файл: [ai/product_analyzer.py](../ai/product_analyzer.py)

Это **ядро бизнес-логики**: по профилю клиента определить, какой продукт ему выгоднее всего.

### 7.1 Каталог продуктов (`self.products`)

Словарь, где для каждого продукта хранятся его параметры:

| Продукт | Ключевые параметры |
|---|---|
| Карта для путешествий | 4% кешбэк на «Путешествия», «Такси» |
| Премиальная карта | 2% базовый кешбэк, 4% на ювелирку, косметику, рестораны; пороги баланса 1 млн и 6 млн ₸; бесплатные снятия |
| Кредитная карта | лимит 2 млн ₸, до 10% на «Играем дома», «Смотрим дома», «Кино»; рассрочка |
| Обмен валют | операции `fx_buy`, `fx_sell` |
| Кредит наличными | 12% на год, 21% свыше года |
| Депозит Мультивалютный | 14,5%, валюты KZT/USD/RUB/EUR, гибкий |
| Депозит Сберегательный | 16,5%, без снятия |
| Депозит Накопительный | 15,5%, пополнение без снятия |
| Инвестиции | от 6 ₸, без комиссии |
| Золотые слитки | операции `gold_buy_out`, `gold_sell_in` |

У каждого продукта есть `description` — короткое описание для уведомления.

**Почему каталог отдельно от логики:** условия продуктов меняются (ставки, категории кешбэка). Их можно поправить в одном месте, не переписывая алгоритм. В будущем каталог легко вынести в JSON или базу данных.

### 7.2 `analyze_products(client_data)`

```python
for product_name, product_info in self.products.items():
    scores[product_name] = self._calculate_product_score(client_data, product_name, product_info)
best_product_name = max(scores, key=scores.get)
```

1. Считает оценку (score) для каждого из 10 продуктов.
2. Выбирает продукт с максимальной оценкой.
3. Возвращает название, оценку, описание и **все оценки** (`all_scores`).

**Почему возвращаются все оценки:** это объяснимость. Можно показать, почему выбран именно этот продукт и какой был вторым — полезно и для отладки, и для аналитиков банка.

### 7.3 `_calculate_product_score(client_data, product_name, product_info)`

Метод устроен как три блока проверок.

#### Блок A — продукты, зависящие от категорий трат (если есть `top_categories`)

**Карта для путешествий**
```
score = Σ (траты в категориях «Путешествия», «Такси») × 0,04 / 1000
```
Логика: выгода клиента = кешбэк, который он получил бы с этой картой. Деление на 1000 — нормализация к «баллам».
*Пример:* 300 000 ₸ на такси за 3 месяца → 12 000 ₸ кешбэка → 12 баллов.

**Премиальная карта**
```
score = (все траты × 0,02 + траты в премиальных категориях × 0,04) / 1000
        + 500, если «баланс» ≥ 1 000 000 ₸
        + 1000, если «баланс» ≥ 6 000 000 ₸ (вместо 500)
```
Логика: премиальная карта выгодна состоятельным клиентам — у них большой остаток (условие обслуживания) и траты на рестораны, косметику, ювелирку.
*Пример:* траты 1,5 млн ₸, из них 300 тыс. ₸ в ресторанах, месячный приход 1,2 млн ₸ → (30 000 + 12 000) / 1000 + 500 = 542 балла.

**Кредитная карта**
```
score = 500, если в топе ≥ 3 категорий
        + траты на «Играем дома», «Смотрим дома», «Кино» × 0,10 / 1000
```
Логика: кредитка с повышенным кешбэком в выбранных категориях выгодна тем, у кого разнообразные траты и есть онлайн-развлечения.

#### Блок B — продукты, зависящие от переводов

**Обмен валют**: +100, если у клиента есть входящие или исходящие переводы.

**Депозиты (все три)**:
- +200, если за 3 месяца пришло больше 100 000 ₸ — есть стабильный приход;
- +300, если «баланс» больше 500 000 ₸ — есть свободные деньги.

Логика: депозит нужен тому, у кого остаются свободные деньги.

**Инвестиции**:
- +200, если возраст меньше 25 (молодые клиенты, студенты — низкий порог входа от 6 ₸);
- +100, если пришло больше 50 000 ₸.

**Золотые слитки**: +150, если пришло больше 200 000 ₸ — золото как способ сохранения капитала для клиентов с высоким доходом.

#### Блок C — кредит наличными

```
если total_transfer_out > «баланс» × 1,2:  score += 500
иначе:                                       score = 0
```
Логика: кредит рекомендуется **только** если клиент тратит заметно больше, чем получает. Сброс в 0 — защита от навязывания кредита тем, кому он не нужен. Это этически важное правило для банка.

#### Финал

`return max(0, score)` — оценка никогда не бывает отрицательной.

### 7.4 Почему выбран подход на правилах

- **Прозрачность.** Каждое решение можно объяснить клиенту, менеджеру и регулятору: «вам предложена карта, потому что вы тратите X на такси».
- **Мало данных.** 60 клиентов — слишком мало, чтобы обучить ML-модель без переобучения.
- **Экспертное знание.** Правила напрямую отражают условия продуктов банка.

### 7.5 Особенности текущей реализации

- В топе почти всегда 5 категорий, поэтому кредитная карта у каждого получает +500 «за разнообразие» — и почти всегда выигрывает.
- Оценки разнородны: одни в «тенге / 1000» (кешбэк даёт единицы и десятки баллов), другие — фиксированные бонусы в сотни баллов. Поэтому продукты сравниваются некорректно.
- Три депозита получают одинаковую оценку; при равенстве `max` выбирает тот, что раньше в словаре.
- Для «Обмена валют» и «Золота» в каталоге перечислены типы операций (`fx_buy`, `gold_buy_out`…), но в расчёте они не используются.
- Для «Кредита наличными» трёхмесячные расходы сравниваются с месячным приходом.

## 8. Модуль `ai/recommendations.py` — генерация пуша

Файл: [ai/recommendations.py](../ai/recommendations.py)

### 8.1 Ленивая загрузка модели (`_load_model`)

```python
model_name = "EleutherAI/gpt-neo-125M"
tokenizer = None
model = None

def _load_model():
    global tokenizer, model
    if tokenizer is None or model is None:
        tokenizer = AutoTokenizer.from_pretrained(model_name)
        model = AutoModelForCausalLM.from_pretrained(model_name)
```

**Как работает:** модель и токенизатор хранятся в глобальных переменных. При первом вызове они загружаются (при самом первом запуске — скачиваются с Hugging Face и кэшируются на диске), при следующих — переиспользуются.

**Почему так:**
- Загрузка модели занимает секунды и сотни мегабайт памяти. Делать её на каждого из 60 клиентов недопустимо.
- Импорт модуля не запускает тяжёлую загрузку — это ускоряет старт и тесты, которым модель не нужна.

**Почему GPT-Neo 125M:**
- Открытая и бесплатная, без API-ключей.
- Работает **локально** — персональные данные клиентов не уходят на сторонние серверы.
- Маленькая (125 млн параметров) — запускается на обычном ноутбуке без GPU.

### 8.2 `llm_generate_push(name, product, top_categories, benefit_sum)`

#### Шаг 1. Нормализация категорий

```python
if isinstance(top_categories, str):
    top_categories = [cat.strip() for cat in top_categories.split(",")]
elif not top_categories:
    top_categories = ["Общие траты"]
top_categories = top_categories[:3]
```
Функция принимает категории и строкой, и списком; пустой список заменяется заглушкой. Берутся максимум три — больше в короткий пуш не поместится.

#### Шаг 2. Промпт

В промпт передаются имя, продукт, категории, выгода и правила редполитики:
- дружелюбно, по делу;
- 180–220 символов;
- без капса, не более одного «!», 0–1 эмодзи;
- даты в формате дд.мм.гггг;
- числа с разделением разрядов пробелом, дроби через запятую, валюта через пробел (`1 000,50 ₸`);
- призыв к действию: «Открыть», «Настроить» или «Посмотреть».

Промпт заканчивается на `Push: ` — модель должна продолжить текст именно с этого места.

#### Шаг 3. Генерация

```python
model.generate(
    input_ids,
    max_length=input_ids.shape[1] + 50,
    do_sample=True, top_k=50, top_p=0.95, temperature=0.8,
    pad_token_id=tokenizer.eos_token_id,
)
```

| Параметр | Значение | Зачем |
|---|---|---|
| `max_length` | длина промпта + 50 токенов | ограничение длины ответа |
| `do_sample=True` | случайная выборка | тексты разнообразны, а не одинаковы для всех |
| `top_k=50` | выбор из 50 самых вероятных токенов | отсекает совсем случайные слова |
| `top_p=0.95` | nucleus sampling | берутся токены, покрывающие 95% вероятности |
| `temperature=0.8` | чуть ниже 1 | баланс между креативностью и связностью |
| `pad_token_id=eos` | | у GPT-Neo нет pad-токена, без этого будет предупреждение |

`torch.no_grad()` отключает расчёт градиентов: модель только предсказывает, не обучается — это экономит память и время.

#### Шаг 4. Извлечение ответа

```python
output = tokenizer.decode(generated_ids[0], skip_special_tokens=True)
push = output.split("Push:")[1].strip().split("\n")[0]
```
Модель возвращает промпт вместе с продолжением, поэтому берётся только текст после `Push:` и только первая строка.

#### Шаг 5. Запасной вариант (fallback)

Если ответ пустой, короче 10 символов или генерация упала с ошибкой — возвращается шаблон:
`"{name}, рекомендуем {product}. Оформить сейчас."`

**Почему:** система никогда не оставит клиента без уведомления, даже если модель не справилась.

### 8.3 Особенности

- GPT-Neo 125M — «продолжатель текста» (causal LM), а не модель, выполняющая инструкции, и обучена в основном на английском. Поэтому правила из промпта она не соблюдает, а русский текст получается бессвязным.
- 50 токенов — это меньше требуемых 180–220 символов русского текста.
- Шаблон fallback использует призыв «Оформить», которого нет в списке разрешённых.
- Импорты `pandas` и `csv` в модуле не используются.

## 9. Модуль `myapp/models.py` — модели данных Django

Файл: [myapp/models.py](../myapp/models.py)

Задел под следующий этап: веб-сервис с базой данных вместо CSV-файлов. Описаны три таблицы.

### `ClientProfile` — профиль клиента

| Поле | Тип | Комментарий |
|---|---|---|
| client_code | CharField, unique | уникальный код |
| name | CharField | имя |
| status | CharField + choices | student / salary / premium / standard |
| age | PositiveIntegerField, 18–120 | валидаторы не дадут сохранить некорректный возраст |
| city | CharField | |
| avg_monthly_balance_KZT | DecimalField(15, 2) | средний баланс |
| created_at / updated_at | DateTimeField | автоматически при создании/изменении |

### `Transaction` — покупки

`date`, `category` (24 категории), `amount`, `currency` (KZT/USD/EUR/RUB), `client` → ForeignKey на `ClientProfile`.
Индексы: `(client, date)` и `(category)`. Сортировка по умолчанию — новые сверху.

### `Transfer` — переводы

`date`, `type` (22 типа операций), `direction` (in/out), `amount`, `currency`, `client`.
Индексы: `(client, date)`, `(type)`, `(direction)`.

### Почему спроектировано так

- **`DecimalField` для денег** — в отличие от `float`, не даёт ошибок округления (0,1 + 0,2 ≠ 0,3 во float). Для финансов это обязательно.
- **`choices`** — в базу нельзя записать несуществующую категорию или тип операции; в админке отображаются человекочитаемые названия.
- **`ForeignKey` с `on_delete=CASCADE`** — при удалении клиента удаляются и его операции, в базе не остаётся «осиротевших» записей.
- **`related_name`** — удобный доступ: `client.transactions.all()`, `client.transfers.all()`.
- **Составной индекс `(client, date)`** — основной запрос системы «операции клиента за период» выполняется быстро даже на миллионах строк.
- **`verbose_name` на русском** — готовая русскоязычная админка Django.

## 12. Известные ограничения

1. **Перекос в сторону кредитной карты** из-за фиксированного бонуса +500 за ≥ 3 категорий в топе.
2. **Несопоставимые шкалы оценок** между продуктами.
3. **Типы переводов не используются** (fx, золото, инвестиции, депозиты, кредиты).
4. **«Баланс» = месячный приход**, а не реальный остаток.
5. **Статус и возраст** не влияют на выбор (возраст всегда 30).
6. **Нет конвертации валют.**
7. **Выгода в пуше = score × 1000** — не реальная сумма.
8. **Модель генерации не подходит** для русского языка и инструкций.
9. **Нет обработки отсутствующего файла** транзакций.
10. **Нет тестов**, есть неиспользуемые импорты и захардкоженные пути.

## 13. Вопросы комиссии и ответы

**Почему правила, а не машинное обучение?**
Правила прозрачны и объяснимы — это критично для банка и регулятора. 60 клиентов недостаточно для обучения модели без переобучения. Архитектура позволяет заменить блок скоринга на ML, когда появится больше данных.

**Как вы оцениваете качество?**
Сравниваем рекомендацию с эталонной колонкой `product`. Сейчас 10%; основные причины найдены (см. раздел 12) и есть план исправления. Колонка используется только для проверки, а не как признак — иначе была бы утечка ответа.

**Почему выбрана именно эта языковая модель?**
Бесплатная, работает локально (данные клиентов не покидают контур), не требует GPU. Ограничение — качество русского текста — нам известно; решение — шаблоны или русскоязычная/инструктивная модель с валидацией.

**Как гарантируется соблюдение редполитики?**
Сейчас — только через промпт, этого недостаточно. Нужен валидатор после генерации: длина, количество «!», эмодзи, формат чисел, разрешённый CTA. При нарушении — повторная генерация или шаблон.

**Что будет, если у клиента нет данных?**
Обработка не падает: клиент получает пометку «Ошибка обработки», остальные обрабатываются. Следующий шаг — работать с тем, что есть (например, только с переводами).

**Как это масштабируется?**
Модули независимы. Django-модели с индексами готовы для переноса данных в БД. Расчёт по клиентам независим — его легко распараллелить.

**Как защищены персональные данные?**
Вся обработка локальная, модель работает офлайн, внешних API нет.

**Почему кредит наличными так редко рекомендуется?**
Это осознанное решение: кредит предлагается только при явной нехватке средств (расходы > доходов × 1,2), иначе оценка обнуляется. Банк не должен навязывать долговую нагрузку.

## 14. План развития

1. **Единая шкала — выгода в тенге за месяц.** Для каждого продукта считать реальную выгоду:
   - карты — кешбэк по фактическим категориям;
   - депозиты — процент на свободный остаток;
   - обмен валют — экономия на спреде по `fx_buy`/`fx_sell`;
   - премиальная карта — кешбэк + экономия на снятиях (`atm_withdrawal`);
   - кредит — только при дефиците средств.
   Эту же сумму честно показывать в пуше.
2. **Использовать типы переводов и статус клиента** как признаки.
3. **Шаблоны пушей** по каждому продукту + валидатор редполитики; LLM — как опция.
4. **Надёжность:** обработка отсутствующих файлов, конвертация валют, автоматический список клиентов из папки, пути из параметров.
5. **Метрика и тесты:** скрипт точности по колонке `product`, unit-тесты на скоринг и форматирование.
6. **Веб-слой:** подключить Django, загрузку CSV в БД и API для получения рекомендаций.
